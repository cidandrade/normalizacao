Do pedido bagunçado à terceira forma normal

A Papelaria Ponto Final controla as vendas numa única planilha. Cada pedido ocupa uma ficha com tudo junto: cliente, vendedor e itens comprados. Funciona… até alguém precisar mudar alguma coisa.

A ficha de pedidos

As colunas marcadas em verde já denunciam o primeiro problema: o endereço é um atributo composto, os telefones são multivalorados e os itens formam um grupo que se repete dentro do mesmo pedido.

O que dá errado com essa planilha

Anomalia de inserção

A loja comprou estojos, mas não consegue cadastrá-los: não existe linha para um produto que ainda não apareceu em nenhum pedido.

Anomalia de atualização

A Ana trocou de e-mail. O novo e-mail precisa ser corrigido em todos os pedidos dela; se alguém esquecer um, o banco passa a ter dois e-mails para a mesma pessoa.

Anomalia de exclusão

Ao apagar o pedido 1002, somem junto o único registro do cliente Bruno e da vendedora Marina.

Normalizar é responder “quem determina quem?”Por isso o primeiro passo não é sair dividindo tabelas. É encontrar as chaves e as dependências funcionais. Todas as decisões das próximas etapas saem delas.

Identificar chaves e dependências funcionais

Uma dependência funcional X → Y diz que cada valor de X corresponde a um único valor de Y. Conhecendo X, você sabe Y.

Mapa de dependências

Estes são os atributos da ficha. Escolha uma dependência na lista abaixo para ver o determinante (preenchido) e o que ele determina (contornado).

    Chaves candidatas, primárias e alternativas

    Uma chave candidata é um conjunto mínimo de atributos que determina todos os outros de um mesmo assunto. Escolhemos uma como primária; as demais viram alternativas (no SQL, UNIQUE).

    Primeira Forma Normal (1FN)

    RegraTodo atributo deve ser atômico: nada de atributos compostos, multivalorados ou grupos repetitivos.

    1. Atributo composto: decompor no próprio lugar

      endereço vira seis atributos simples. Nenhuma tabela nova é criada.

      endereço⇒logradouronumerobairrocidadeufcep

    2. Atributo multivalorado: nova tabela

      A chave da nova tabela é a chave de quem determina o atributo mais o próprio valor. A DF4 mostra que os telefones dependem do cliente, não do pedido. Por isso a tabela leva cpfCliente, e não numPedido.

      cpfCliente→→telefone⇒CLIENTE_TELEFONE(cpfCliente, telefone)

    3. Grupo repetitivo: nova tabela

      Os itens saem para uma tabela própria. A chave é a da tabela de origem (numPedido) mais a chave do grupo (codProduto).

      numPedido+codProduto⇒ITEM_PEDIDO

    Resultado da 1FN

    Repare em duas chaves estrangeiras que já surgiram: ITEM_PEDIDO.numPedido aponta para PEDIDO. Já CLIENTE_TELEFONE.cpfCliente ainda não tem para onde apontar, porque a tabela de clientes só nasce na 3FN. Fica anotada como pendente.

    A redundância aumentou?

    Sim. Ao separar o endereço em seis colunas, os dados repetidos da Ana ficaram mais visíveis. A 1FN resolve a atomicidade, não a redundância. Quem ataca a redundância são a 2FN e a 3FN.

    Segunda Forma Normal (2FN)

    RegraEstar na 1FN e todo atributo não-chave depender da chave primária inteira, e não de parte dela.

    Dependência parcial só existe quando há uma parte da chave para depender. Então só tabelas com chave composta precisam ser examinadas.

    A decomposição

    Os atributos com dependência parcial saem junto com o seu determinante, codProduto, que vira chave primária da nova tabela PRODUTO. Em ITEM_PEDIDO, codProduto continua na chave e passa a ser também chave estrangeira. A chave alternativa ean (DF7) acompanha o produto.

    codProduto→ean, descricao, precoTabela⇒PRODUTO

    Resultado da 2FN

    Por que existem dois preços?

    precoTabela é o preço atual do produto e depende só de codProduto. precoVendido é o preço praticado naquele pedido (com desconto, por exemplo) e depende da chave inteira. Se a loja reajustar a caneta amanhã, o histórico dos pedidos não muda.

    Terceira Forma Normal (3FN)

    RegraEstar na 2FN e nenhum atributo não-chave depender de outro atributo não-chave. Ou seja: sem dependências transitivas.

    Examinando PEDIDO

    Em PEDIDO, o CPF e a matrícula não são chave, mas determinam outros atributos. Formam-se duas cadeias:

    numPedido→cpfCliente→nomeCliente, emailCliente, logradouro, numero, bairro, cidade, uf, cep
    numPedido→matVendedor→nomeVendedor

    Cada atributo do meio da cadeia vira chave primária de uma tabela nova, levando o que ele determina. Na tabela de origem ele permanece como chave estrangeira.

    As outras tabelas

    TabelaAnálise
    ITEM_PEDIDONa 3FN. quantidade e precoVendido não determinam um ao outro.
    CLIENTE_TELEFONENa 3FN. Não tem atributos não-chave.
    PRODUTONa 3FN. Existe ean → descricao, mas ean é chave alternativa, não um atributo não-chave. Quando o determinante é chave candidata, não há transitividade.
    CLIENTE (nova)Na 3FN. emailCliente determina os demais, mas também é chave candidata.

    Resultado da 3FN

    Para discutir em aula: e o CEP?

    Na maioria dos casos, o CEP determina bairro, cidade e UF. Seria, então, mais uma dependência transitiva dentro de CLIENTE: cpfCliente → cep → cidade. Separar uma tabela de CEPs é correto em teoria, mas muitos projetos mantêm o endereço junto por simplicidade, sobretudo quando não há uma base oficial de CEPs para manter. É uma decisão de projeto, e vale a pena justificá-la na documentação.

    Verificar as chaves estrangeiras

    Toda decomposição deixa um elo para trás: o determinante que virou chave primária da tabela nova continua na tabela de origem, agora como chave estrangeira. É por esse elo que os dados voltam a se juntar.

    Chave estrangeiraReferenciaSurgiu naLeitura
    ITEM_PEDIDO.numPedidoPEDIDO.numPedido1FN1 pedido tem N itens
    CLIENTE_TELEFONE.cpfClienteCLIENTE.cpfCliente1FN, concluída na 3FN1 cliente tem N telefones
    ITEM_PEDIDO.codProdutoPRODUTO.codProduto2FN1 produto aparece em N itens
    PEDIDO.cpfClienteCLIENTE.cpfCliente3FN1 cliente faz N pedidos
    PEDIDO.matVendedorVENDEDOR.matVendedor3FN1 vendedor atende N pedidos

    Para cada chave estrangeira, confira

    • Ela aponta para a chave primária (ou alternativa) de uma tabela que existe. A pendência da 1FN foi resolvida quando CLIENTE nasceu.
    • Tem o mesmo domínio e o mesmo tipo da chave referenciada (CHAR(14) com CHAR(14)).
    • A obrigatoriedade faz sentido: todo pedido tem cliente e vendedor, então as duas são NOT NULL.
    • A cardinalidade lida em voz alta faz sentido para o negócio.
    • Nenhum determinante ficou “solto”: cada tabela criada na decomposição está ligada à sua origem.

    Nenhuma dependência se perdeu

    Cada dependência funcional identificada no passo 1 precisa caber inteira em alguma tabela, para que o banco consiga garanti-la.

    Nenhuma informação se perdeu

    Juntando as tabelas pelas chaves estrangeiras, a ficha original tem que voltar, sem linhas a mais nem a menos.

    SELECT p.numPedido, p.dataPedido, c.nomeCliente, c.emailCliente, c.cidade,
       v.nomeVendedor, pr.descricao, i.quantidade, i.precoVendido
FROM PEDIDO p
JOIN CLIENTE     c  ON c.cpfCliente  = p.cpfCliente
JOIN VENDEDOR    v  ON v.matVendedor = p.matVendedor
JOIN ITEM_PEDIDO i  ON i.numPedido   = p.numPedido
JOIN PRODUTO     pr ON pr.codProduto = i.codProduto
ORDER BY p.numPedido, pr.codProduto;

    Ver o script SQL de criação

    Repare na ordem: as tabelas referenciadas são criadas antes das que as referenciam. Essa é mais uma forma de conferir as chaves estrangeiras.

    CREATE TABLE CLIENTE (
  cpfCliente   CHAR(14)     PRIMARY KEY,
  nomeCliente  VARCHAR(100) NOT NULL,
  emailCliente VARCHAR(120) NOT NULL UNIQUE,
  logradouro   VARCHAR(120) NOT NULL,
  numero       VARCHAR(10)  NOT NULL,
  bairro       VARCHAR(60)  NOT NULL,
  cidade       VARCHAR(60)  NOT NULL,
  uf           CHAR(2)      NOT NULL,
  cep          CHAR(9)      NOT NULL
);

CREATE TABLE CLIENTE_TELEFONE (
  cpfCliente CHAR(14)    NOT NULL,
  telefone   VARCHAR(20) NOT NULL,
  PRIMARY KEY (cpfCliente, telefone),
  FOREIGN KEY (cpfCliente) REFERENCES CLIENTE (cpfCliente)
);

CREATE TABLE VENDEDOR (
  matVendedor  CHAR(3)      PRIMARY KEY,
  nomeVendedor VARCHAR(100) NOT NULL
);

CREATE TABLE PRODUTO (
  codProduto  CHAR(3)       PRIMARY KEY,
  ean         CHAR(13)      NOT NULL UNIQUE,
  descricao   VARCHAR(100)  NOT NULL,
  precoTabela DECIMAL(10,2) NOT NULL
);

CREATE TABLE PEDIDO (
  numPedido   INT      PRIMARY KEY,
  dataPedido  DATE     NOT NULL,
  cpfCliente  CHAR(14) NOT NULL,
  matVendedor CHAR(3)  NOT NULL,
  FOREIGN KEY (cpfCliente)  REFERENCES CLIENTE (cpfCliente),
  FOREIGN KEY (matVendedor) REFERENCES VENDEDOR (matVendedor)
);

CREATE TABLE ITEM_PEDIDO (
  numPedido    INT           NOT NULL,
  codProduto   CHAR(3)       NOT NULL,
  quantidade   INT           NOT NULL CHECK (quantidade > 0),
  precoVendido DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (numPedido, codProduto),
  FOREIGN KEY (numPedido)  REFERENCES PEDIDO (numPedido),
  FOREIGN KEY (codProduto) REFERENCES PRODUTO (codProduto)
);
